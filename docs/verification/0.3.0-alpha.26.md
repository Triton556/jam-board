# 0.3.0-alpha.26 — scoped move-result recovery

## Scope and deliberate tradeoff

An independent frozen-alpha25 hook/QueryClient probe reproduced an old move error
restoring an entire project-A board snapshot under selected project B, including
when B's recovery read failed. A→B→A and unmounted completion also restored stale
cache. A modeled persistence-then-notification rejection falsely looked like a
failed move and rolled back the displayed committed state. These are DOM/query
and modeled-transport proofs, not an induced native notification failure.

Each move now captures its input and project selection generation at invocation.
Pre-dispatch, notices, readiness requests and completion reads require the same
mounted view and generation. A→B→A does not revive an old attempt. An already sent
request is not cancelled; stale callbacks cannot repopulate the new view.

There are no speculative board-cache writes or snapshot rollbacks. Cards stay at
last-read/event positions while the board says it is saving and refreshing. This
is a deliberate small latency/visual-feedback tradeoff, not a new optimistic
transaction ledger. Multiple in-flight moves retain pending feedback and cannot
restore one another's snapshots. Read-only reconciliation follows a current-view
result; a failed read leaves the last observed data and existing Try again action.
Known conflict, readiness and execution-required refusals keep their policies.
Other errors conservatively mean an unconfirmed result, with a dismissible notice
within the existing three-notice session bound. No automatic mutation retry occurs.

No backend, schema, identity, permissions, animation or new Move-menu change is
included. Drag input, captured updatedAt, destination-neighbor calculation and
Ready dialog routing are preserved. This is not a complete accessibility claim.

## Limits

The frontend tests use Happy DOM, synthetic key input and controlled bridge/query
responses. They do not establish native notification-failure injection, actual
cross-project database writes, geometry, AX, or current Windows/macOS acceptance.
Earlier native alpha25 acceptance remains attributed to runtime819ffdb and its
package; it is not relabelled as this version's acceptance. Native follow-up and
current external CI are separate checkpoints until their actual results arrive.

The application still cannot generally distinguish an error before persistence
from a notification/transport error afterward. This repair makes Board's handling
honest without redesigning execute_with_store, idempotency or all other mutations.
Leaving the view invalidates its callbacks, not the underlying write. Inspect fresh
state in the intended project before another deliberate move if you left while
waiting. No receipt is guaranteed after page/app exit, and the in-memory notice
limit is not an operation journal.
