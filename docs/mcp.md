# Jam Board MCP

Plan your game jam with your AI teammates. Both transports invoke the same `jam-core` services and SQLite transactions as the desktop application. There is no cloud service, account, or telemetry.

## Build and connect

From the repository root:

```powershell
cargo build -p jam-mcp-cli
$env:JAM_BOARD_DATA_DIR = Join-Path (Get-Location) '.dev-data'
.\target\debug\jam-board-mcp.exe --seed-demo
```

`--seed-demo` explicitly creates a new demo jam before serving stdio. Omit it for normal use. The process waits for MCP input; human-readable logging goes to stderr and `<data-dir>/logs/mcp-stdio.log`. stdout contains only JSON-RPC protocol messages. Closing stdin terminates the process.

Database lookup order:

1. `--db <path>` (a database file, not a directory).
2. `JAM_BOARD_DB`.
3. `JAM_BOARD_DATA_DIR/jam.db`.
4. `%APPDATA%/dev.triton556.jamboard/jam.db`.

Use an absolute development data path in agent configuration because clients may start the process from another working directory. Real Codex/Claude configuration files are never edited by this project.

### Codex: stdio (installed application)

```toml
[mcp_servers.jam-board]
command = "C:\\Users\\<you>\\AppData\\Local\\Jam Board\\jam-board-mcp.exe"
env = { JAM_AGENT_NAME = "Codex" }
```

### Codex: HTTP (desktop must be open)

```toml
[mcp_servers.jam-board-http]
url = "http://127.0.0.1:47321/mcp"
bearer_token_env_var = "JAM_BOARD_TOKEN"
http_headers = { "X-Jam-Agent" = "Codex" }
```

Set `JAM_BOARD_TOKEN` in the environment inherited by the client to the token copied explicitly from Settings ? MCP. Do not commit the token. `bearer_token_env_var` and `http_headers` are supported by the [official Codex MCP configuration documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

### Claude Code: stdio

```powershell
claude mcp add jam-board --env JAM_AGENT_NAME=Claude -- '<path-to-installed-jam-board-mcp.exe>'
```

### Claude Code: HTTP

```powershell
claude mcp add --transport http jam-board http://127.0.0.1:47321/mcp --header "Authorization: Bearer <token>" --header "X-Jam-Agent: Claude"
```

The name-before-`--env` stdio form and HTTP header form follow the [official Claude Code MCP guide](https://code.claude.com/docs/en/mcp). Replace `<token>` locally; if the default port is occupied, use the actual port stored in `settings.mcp_http_port`. These are instructions for the user, not commands that this implementation runs against real agent configuration.

Replace the executable path with the absolute path shown in Settings ? MCP. TOML does not expand %LOCALAPPDATA%; the example is a placeholder, not a literal path to paste unchanged. Installed stdio needs no data override. For development, add JAM_BOARD_DATA_DIR pointing at <checkout>/.dev-data. The default data folder is %APPDATA%\dev.triton556.jamboard.

## Transports and authentication

`jam-board-mcp` uses rmcp stdio. The desktop owns the Streamable HTTP server; it runs only while the desktop is open and `mcp_http_enabled=true` (the default). It binds exclusively to IPv4 loopback, `/mcp`, initially port 47321. Occupied ports fall back through 47322–47330; a successful port is persisted and preferred on restart.

Every HTTP request, including initialize, GET/SSE and DELETE, requires `Authorization: Bearer <token>`. Missing/incorrect credentials return HTTP 401. If Origin is present, it must be `http://127.0.0.1:<port>` or `http://localhost:<port>` with a valid numeric port; all other values return 403. Absence of Origin is permitted for native clients. The token file contains 32 cryptographically generated bytes encoded as base64url without padding (43 characters), created once and reused.

MCP lifecycle and framing are handled by [rmcp 3.5.1](https://docs.rs/rmcp/3.5.1/rmcp/). The integration suite exercises `initialize` with protocol 2025-06-18, alongside rmcp's supported version negotiation. No bespoke JSON-RPC server is used.

## Identity and presence

The initialized `clientInfo.name` determines the client kind: names containing `codex` map to `codex`, containing `claude` to `claude-code`, otherwise `other` (case-insensitive). Stdio `JAM_AGENT_NAME` or HTTP `X-Jam-Agent` overrides the display name. Defaults are `Codex`, `Claude`, or `clientInfo.name`.

An unknown agent handle is registered with `member.joined`, taking the first unused member color. Each call refreshes `lastSeenAt`. Agents are online for 120 seconds after their latest call. Handles are stable across sessions; a human handle cannot be impersonated by registering an agent with the same name.

## Tool contract

All tool argument objects use camelCase, reject unknown properties, and are described with schemars-generated JSON Schema. Task addresses are keys (`JB-12`), never ULIDs. A missing active jam is `not_found`.

Successful results contain both `structuredContent` (the JSON data below) and a short `content` text summary. Errors are successful JSON-RPC responses with `isError: true` and readable text; they do not crash the server. Codes are `not_found`, `claim_conflict` (including the holder's name), `validation` (field and reason), and `archived`. Unexpected storage failures are reported as readable `storage` errors rather than terminating the process.

| Tool | Arguments | Structured content |
|---|---|---|
| `get_board` | `{}` | Board summary |
| `list_tasks` | `status?: string[]`, `assignee?: string`, `tag?: string`, `query?: string`, `includeArchived?: boolean = false`, `limit?: integer = 50`, `cursor?: string` | `{ tasks: TaskSummary[], nextCursor?: string }` |
| `get_task` | `key: string` | `TaskDetail` |
| `create_task` | `title: string`, `description?: string`, `status?: string = "todo"`, `priority?: string = "medium"`, `tags?: string[]`, `estimate?: integer`, `dueAt?: string`, `idempotencyKey?: string` | `TaskDetail` |
| `update_task` | `key: string`, `title?: string`, `description?: string`, `priority?: string`, `tags?: string[]`, `estimate?: integer \| null`, `dueAt?: string \| null` | `TaskDetail` |
| `move_task` | `key: string`, `status: string`, `beforeKey?: string`, `afterKey?: string` | `TaskSummary` |
| `claim_task` | `key: string` | `TaskDetail` |
| `release_task` | `key: string`, `status?: string = "todo"` | `TaskSummary` |
| `add_comment` | `key: string`, `body: string` | `Comment` |
| `archive_task` | `key: string`, `reason?: string` | `TaskSummary` |
| `list_members` | `{}` | `MemberStats[]` |
| `list_assets` | `kind?: string`, `query?: string` | `Asset[]` |

Statuses: `backlog`, `todo`, `in_progress`, `review`, `done`. Priorities: `low`, `medium`, `high`, `critical`. Estimates: 1, 2, 3, 5, 8. Asset kinds: `sprite`, `audio`, `level`, `font`, `other`. Titles contain 1–140 Unicode characters, comments 1–4000; blank-only text is invalid. Tags are trimmed, lowercased, deduplicated, sorted, and limited to 24 characters each. Empty tags are omitted. Timestamp input is RFC 3339 and is stored in UTC.

`list_tasks.assignee` accepts a handle, `me`, or `unassigned`. `query` is a case-insensitive literal substring in title or description. Tags are exact normalized matches. Archived tasks are hidden by default. Limit must be 1–200. Return `nextCursor` unchanged on the next call with the same filters. Cursors are offsets, so concurrent reordering can change page membership.

`update_task.tags` replaces the list. Omitted nullable fields are preserved; explicit null clears estimate/dueAt. Description is supplied as `description` and returned as `descriptionMd`.

`move_task` appends when no neighbors are supplied. `afterKey` immediately precedes the task; `beforeKey` immediately follows it. Neighbors must be active, in the destination jam/column, and adjacent when both are supplied. A small position gap triggers transactional column renumbering.

`claim_task` rejects another holder atomically, otherwise assigns the caller and promotes backlog/todo to in_progress. Claiming an already-held own task is permitted. `release_task` requires the holder or a human and clears assignment. No MCP tool can arbitrarily assign another member or unarchive. `archive_task.reason` is a comment covered by the same single archive event. All subsequent mutations on an archived task fail; humans can restore through the domain service.

Retrying `create_task` with the same `(agent, idempotencyKey)` returns the original task and appends no event, including when other create fields differ. Keep the key unique for each logical request.

### Result shapes

```typescript
type MemberRef = { id: string; kind: "human" | "agent"; name: string; handle: string; color: string };
type Member = MemberRef & {
  avatar: string | null; client: string | null;
  lastSeenAt: string | null; createdAt: string;
};
type MemberStats = Member & { counts: Record<string, number>; online: boolean; workingOn: string[] };
type TaskSummary = {
  id: string; jamId: string; key: string; title: string; descriptionMd: string;
  status: string; priority: string; estimate: number | null; dueAt: string | null;
  position: number; assigneeId: string | null; createdBy: string; updatedBy: string;
  createdAt: string; updatedAt: string; archivedAt: string | null;
  idempotencyKey: string | null; tags: string[];
};
type TaskDetail = TaskSummary & { assets: Asset[]; comments: Comment[]; activity: ActivityEvent[]; history: ActivityEvent[] };
type Comment = { id: string; taskId: string; authorId: string; bodyMd: string; createdAt: string };
type Asset = {
  id: string; jamId: string; kind: string; name: string; location: string;
  notes: string | null; createdBy: string; createdAt: string;
};
type ActivityEvent = {
  seq: number; action: string; actor: MemberRef; taskKey?: string;
  payload: JsonValue; createdAt: string;
};
type JsonValue = null | boolean | number | string | JsonValue[] | { [key: string]: JsonValue };
type BoardTask = { key: string; title: string; priority: string; status: string; assignee: MemberRef | null };
type Board = {
  jam: { name: string; theme: string | null; endsAt: string | null; timeLeft: number | null };
  columns: { status: string; count: number }[];
  inProgress: BoardTask[]; myTasks: BoardTask[]; onlineAgents: MemberStats[];
};
```

`activity` retains the latest 20 task events for existing clients. M4 adds `history`, containing up to the latest 50 task events; both arrays are chronological. `updatedAt` is an opaque version string for desktop optimistic locking and must not be rounded. `seq` is the monotonic database cursor. Activity is committed in the same transaction as the mutation, exactly once. Agent registration is a separate mutation; heartbeat metadata is not another event.

## Resources

`resources/list` announces `jam://board` (`text/markdown`): active jam name/theme, column counts, and in-progress tasks.

`resources/templates/list` announces `jam://task/{key}` (`text/markdown`). `resources/read` returns the task heading, metadata table (status, priority, assignee, estimate, due, tags), description, and comments with authors/timestamps. Unknown URIs/keys produce readable resource errors.

## Prompt

`work_on_next_task`, optional argument `tag`, instructs the agent to:

1. Call `get_board`.
2. Paginate `list_tasks` with `status=["todo"]`, `assignee="unassigned"`, and the optional tag. Choose highest priority (critical > high > medium > low), breaking ties by board order.
3. Call `claim_task`; on conflict, choose another available task.
4. Perform the work.
5. Call `add_comment` with the result and validation.
6. Call `move_task` with `status="review"`.

## Live desktop events and verification

The desktop checks a dedicated connection's `PRAGMA data_version` every 250 ms. Changes drain `ChangeFeed.poll()` in monotonic sequence order and emit the typed Tauri `board-changed` event with `{ events: ActivityEvent[] }`. The frontend invalidates affected query caches, highlights agent cards for four seconds, pulses avatars for two seconds and shows up to three five-second toasts. The full board, table, task editor and Activity screen share this feed.

```powershell
cargo test -p jam-core
cargo test -p jam-mcp -p jam-mcp-cli
node scripts/m2-smoke.mjs --seed-demo
```

The last command is a real stdio test client and writes [the recorded transcript](media/m2-mcp-transcript.md). Use `--seed-demo` once for an empty development database; omit it thereafter. `--cdp` additionally observes the running application's actual console subscription when WebView2 is launched with process-only loopback diagnostics enabled. Test tooling does not modify real Codex or Claude configurations.

## Runtime settings and call visibility

Settings can stop/restart HTTP without restarting the app and regenerate the token, cancelling old HTTP sessions. Show/Copy are explicit actions; rendered snippets and screenshots mask the token. The sidecar path is resolved beside the installed application.

The last twenty tool calls are kept only in desktop memory. A separate authenticated loopback metadata listener lets stdio report agent/tool/time/result while the window is open, including when HTTP is disabled. No tool arguments or durable call log are stored. An unavailable metadata receiver never prevents a successful MCP tool result. Member online status expires 120 seconds after the latest call.
